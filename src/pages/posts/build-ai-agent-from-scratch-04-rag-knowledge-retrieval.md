> 上一篇构建的 Agent 已经能够循环调用工具，但它仍然不知道企业文档、项目资料和个人文件里写了什么。这一篇解决知识从哪里来的问题：先找到与问题相关的内容，再让模型根据这些内容回答。

## 1. Agent 会使用工具，不等于掌握外部知识

假设我们已经有一个可以调用工具的 Agent，现在问它：

```text
这个项目应该怎样配置数据库？
```

如果答案只存在于项目内部的 `deployment.md`，模型仅凭训练时学到的知识无法可靠回答。最直接的办法，是把整份文档放进提示词：

```text
请根据下面的文档回答问题。

文档：
{{entire_file}}

问题：这个项目应该怎样配置数据库？
```

文件很小时，这个办法简单而且有效。文件多起来以后，问题就出现了：

- 全部内容可能超过模型的上下文窗口。
- 大部分段落与当前问题无关，却仍然消耗 token。
- 无关内容越多，真正有用的信息越容易被淹没。

所以，我们不应该每次都把整个知识库交给模型，而应该先找出最相关的几段内容。

这就是 RAG（Retrieval-Augmented Generation，检索增强生成）的基本思想：

```text
先检索相关资料 → 把资料加入上下文 → 根据资料生成答案
```

RAG 不是某个模型，也不等于某个向量数据库。它首先是一条数据流。

## 2. 一套最小 RAG 分成两个阶段

理解 RAG 最容易混淆的地方，是把“准备知识库”和“回答问题”看成同一件事。实际上，它们通常发生在两个阶段。

### 2.1 建立索引

文档进入系统时，程序先把它切成较小的片段，再把每个片段转换成向量并保存：

```text
原始文档
   ↓
文本切分（Chunking）
   ↓
多个文本片段（Chunks）
   ↓
生成向量（Embedding）
   ↓
保存文本、向量和来源信息
```

这个阶段不需要等待用户提问。只要文档没有变化，向量通常可以重复使用。

### 2.2 检索并生成

用户提出问题以后，程序把问题也转换成向量，再从索引中找出最相关的片段：

```text
用户问题
   ↓
生成问题向量
   ↓
检索最相关的 Chunks
   ↓
问题 + Chunks + 来源信息
   ↓
LLM 生成回答
```

前半段负责“找资料”，后半段负责“写答案”。只有检索而没有生成，通常叫搜索；把检索结果交给模型继续回答，才构成这里讨论的 RAG。

## 3. 搜索知识不只有向量这一种办法

向量搜索很常见，但不是唯一选择。数据形态不同，适合的检索方法也不同。

| 方法 | 主要依据 | 适合的内容 | 主要限制 |
| --- | --- | --- | --- |
| 关键词搜索 | 字面是否匹配 | 函数名、错误码、专有名词 | 不擅长理解近义表达 |
| 向量搜索 | 语义是否接近 | 自然语言文档、问答资料 | 可能漏掉必须精确匹配的词 |
| 结构化搜索 | 目录、文件和字段结构 | 代码仓库、压缩包、表格 | 依赖清楚的数据组织方式 |
| 图搜索 | 实体之间的关系 | 依赖分析、多跳关系问题 | 建图和维护成本较高 |

例如，搜索错误码 `ERR_CONNECTION_42` 时，关键词匹配通常比语义相似度更直接；搜索“怎样连接数据库”时，向量搜索则可能找到使用了“初始化数据源”这类不同措辞的段落。

实际系统经常组合多种方法。关键词搜索负责“必须包含什么”，向量搜索负责“意思是否接近”，结构化搜索负责“应该到哪里找”。

下面先实现一条最小向量检索流程，因为它能清楚展示 RAG 的核心数据流。

## 4. Embedding：把文本转换成可比较的向量

Embedding 可以理解为文本的数字表示。Embedding 模型接收一段文本，返回一个由许多数字组成的向量。程序不直接解释其中某个数字的含义，而是比较不同向量之间的位置关系。

下面是一个最小 TypeScript 示例：

```ts
async function getEmbeddings(texts: string[]): Promise<number[][]> {
  const response = await client.embeddings.create({
    model: "text-embedding-3-small",
    input: texts,
  });

  return response.data.map((item) => item.embedding);
}
```

这段代码一次接收多段文本，再按照响应顺序取出各自的向量。

向量真正有用的地方，是相近含义的文本通常也会得到较接近的表示。例如：

```text
猫睡在沙发上
小猫在客厅休息
汽车在公路上行驶
```

前两句话虽然用词不同，语义却更接近。理想情况下，它们的向量相似度也会高于第三句话。

Embedding 衡量的是模型学到的语义相关性，不是事实正确性。两个片段在谈同一个主题，不代表其中的内容一定真实。

## 5. 用余弦相似度比较两个向量

有了向量，还需要一个评分方法决定哪些文本更接近。常见选择之一是余弦相似度，它比较两个向量的方向。

下面是最小实现：

```ts
function cosineSimilarity(a: number[], b: number[]): number {
  const dot = a.reduce((sum, value, i) => sum + value * b[i], 0);
  const normA = Math.sqrt(a.reduce((sum, value) => sum + value ** 2, 0));
  const normB = Math.sqrt(b.reduce((sum, value) => sum + value ** 2, 0));

  return dot / (normA * normB);
}
```

代码先计算点积，再除以两个向量长度的乘积。对本文的文本检索场景，可以把较高分数理解为语义更接近。

这段代码用于解释原理，还没有处理生产环境中的边界情况。正式实现至少要检查：

- 两个向量的维度是否一致。
- 向量是否为空。
- 向量长度是否为零，避免除以零。
- 大量向量应该怎样批量计算和建立索引。

## 6. Chunking：为什么不能给整份文档只生成一个向量

假设一本手册同时包含安装、数据库、权限和部署四个主题。如果把整本手册压缩成一个向量，这个向量需要同时代表所有内容，检索结果就会变得模糊。

更常见的做法是先切分文档。每一个切分后的片段叫作 Chunk，它既是生成向量的单位，也是搜索返回的单位。

最简单的切分方法，是按照固定字符数截取：

```ts
function fixedLengthChunking(
  text: string,
  chunkSize = 500,
  overlap = 50,
): string[] {
  const chunks: string[] = [];

  for (let start = 0; start < text.length; start += chunkSize - overlap) {
    chunks.push(text.slice(start, start + chunkSize));
  }

  return chunks;
}
```

这里的 `overlap` 表示相邻 Chunk 保留一部分重复内容。如果一句话正好落在切分边界上，重叠区域可以减少上下文被完全截断的概率。

固定长度切分容易实现，却不知道标题、段落和代码块的边界。更完整的切分器通常会优先保留自然结构，例如：

- Markdown 标题和段落。
- 完整句子。
- 函数、类或代码块。
- 表格中的完整记录。

Chunk 并不是越大越好，也不是越小越好。

- 太大：每次检索会带回更多无关内容。
- 太小：一个完整事实可能被拆散，模型看不到必要上下文。

合适的大小、重叠量和返回数量需要根据真实文档与问题集测试，不能只靠一个通用数字决定。

## 7. 实现一个最小向量搜索

知识库准备完成后，每个 Chunk 都包含原文和对应向量：

```ts
type Chunk = {
  text: string;
  embedding: number[];
};
```

查询时，我们为问题生成向量，逐一计算相似度，再返回分数最高的 `topK` 个片段：

```ts
async function vectorSearch(
  query: string,
  chunks: Chunk[],
  topK = 3,
) {
  const [queryEmbedding] = await getEmbeddings([query]);

  return chunks
    .map((chunk) => ({
      text: chunk.text,
      score: cosineSimilarity(queryEmbedding, chunk.embedding),
    }))
    .sort((a, b) => b.score - a.score)
    .slice(0, topK);
}
```

这段代码完整展示了“向量化问题—计算分数—排序—截取结果”的过程。它适合小规模数据和原理演示，但每次查询都要扫描全部 Chunk，数据量增大后会越来越慢。

生产系统通常会使用向量索引或向量数据库加速近邻搜索。不过，基础设施只能提高搜索效率，不能替你决定 Chunk 应该怎样切、返回多少条以及怎样评估结果是否相关。

## 8. 把检索结果交给模型

向量搜索只完成了 Retrieval。接下来还要把搜索结果加入模型输入，完成 Augmented Generation。

下面仍然是最小示意代码：

```ts
async function answerWithRag(question: string, chunks: Chunk[]) {
  const results = await vectorSearch(question, chunks, 3);
  const context = results
    .map((item, index) => `[Source ${index + 1}]\n${item.text}`)
    .join("\n\n");

  return askModel(`
Answer the question using only the sources below.
If the sources are insufficient, say so clearly.

Sources:
${context}

Question: ${question}
  `);
}
```

这里有两个值得保留的设计：

1. 每个片段带有来源编号，便于追踪答案依据。
2. 提示词明确要求资料不足时说明情况，避免模型把缺失信息偷偷补齐。

真正的应用不应该只保存一段 `text`。每个 Chunk 最好同时保留文档 ID、文件名、标题、位置和更新时间等元数据。这样才能在回答中展示引用，也能在结果错误时查出究竟是检索问题、文档问题还是生成问题。

## 9. RAG 为什么仍然可能答错

RAG 给模型提供了外部资料，但没有自动消除错误。一次回答至少会经过三道关口：

```text
问题有没有被正确表示
        ↓
检索有没有找到正确片段
        ↓
模型有没有正确使用这些片段
```

任何一步出错，最终答案都可能不可靠。

常见失败包括：

- **没有召回正确内容**：相关片段根本没有进入上下文。
- **排序不理想**：真正有用的片段排在 `topK` 之外。
- **文档已经过时**：检索结果相关，却不是当前事实。
- **片段缺少上下文**：Chunk 太小，只有结论没有前提。
- **模型忽略资料**：上下文里有答案，模型却使用了自身知识。
- **资料之间互相冲突**：模型没有识别版本或来源差异。

因此，评估 RAG 时要把“检索质量”和“回答质量”分开。先检查正确片段有没有被找回来，再判断模型是否根据片段得出了正确答案。只看最终回答，很难定位问题发生在哪一层。

## 10. Web Search 也可以进入同一条流程

Web Search 返回的标题和摘要有时已经足够回答问题，有时却缺少必要上下文。后一种情况下，可以继续抓取网页正文，再使用相同的 RAG 流程：

1. 搜索并选出候选网页。
2. 获取网页正文，并记录 URL 和时间。
3. 清理导航栏、广告等无关内容。
4. 切分正文并生成 Embedding。
5. 用原始问题检索最相关片段。
6. 把片段和来源交给模型回答。

这能减少整页内容带来的上下文消耗，但同时增加了网络请求、网页解析和索引成本。如果搜索服务已经返回足够完整的相关片段，就没有必要为了形式完整而再做一次向量检索。

网页内容也属于不可信输入。Agent 不应把网页中的命令当成系统指令，更不能因为页面要求就调用高风险工具。检索解决的是“找到内容”，不是“信任内容”。

## 11. 有结构的数据，先使用结构本身

向量搜索不应该成为处理所有文件的默认答案。对于代码仓库、压缩包和表格，目录、文件名、扩展名和字段本身就是强线索。

Agent 可以使用一组文件工具逐步浏览：

```text
unzip_file       解压归档文件
list_files       查看目录结构
read_file        读取文本、CSV 或 Excel
read_media_file  分析图片、音频或 PDF 页面
```

例如，目录中存在 `Job Listing.pdf` 和 `Applicants.xlsx`。文件名已经暗示了两份资料的关系：前者可能是招聘要求，后者可能是候选人信息。Agent 可以先读取职位说明，再从表格中筛选候选人，不一定要提前为所有文件建立向量索引。

结构化搜索的优点是路径清楚、结果容易解释，也能处理不同文件格式。它的限制是 Agent 必须拥有文件工具，并且程序要设置路径白名单、文件大小限制和访问权限。

较完整的系统可以先利用目录缩小范围，再在候选文件内部做关键词或向量检索。不同检索方式是互补关系，不必只能选择一种。

## 12. 用 Callback 把检索接入 Agent 执行流程

上一篇的 Agent 已经拥有循环和执行上下文。把 RAG 接进来后，搜索结果也会成为工具结果，进入下一轮模型上下文。

这时会出现两个工程问题：工具结果可能很长，有些工具也可能涉及敏感操作。Callback（回调）提供了一个扩展位置，让程序在不重写 Agent 核心循环的情况下插入额外逻辑。

常见的前置回调包括：

- 检查工具权限。
- 请求用户批准。
- 查询缓存，命中时跳过真实工具调用。

常见的后置回调包括：

- 记录调用耗时和审计日志。
- 压缩过长的搜索结果。
- 删除敏感字段。
- 为结果补充来源信息。

例如，Agent 准备执行 `delete_file` 时，前置回调可以暂停流程，向用户展示工具名称和参数；只有用户批准后，程序才继续执行。这就是 Human in the Loop，也就是把人工确认放进自动执行流程。

对于检索工具，后置回调可以把冗长结果压缩成标题、URL 和相关片段，再交给下一轮模型。这能控制上下文长度，但压缩后的结果必须保留来源，并留下事件记录。否则，后续很难解释某段内容究竟来自原始文档、缓存还是压缩步骤。

## 13. 把整篇压缩成一张图

```text
知识准备阶段
文档 → 切分 → Embedding → 保存文本、向量和来源

回答问题阶段
问题 → Embedding → 检索 Top K → 组装上下文 → LLM 回答
                         ↓
                   来源与分数用于追踪

Agent 扩展阶段
搜索工具 → Callback → 压缩、权限检查、审计 → 下一轮模型
```

这三条流程分别解决三个问题：知识怎样进入系统、问题怎样找到知识，以及检索能力怎样安全地进入 Agent Loop。

## 总结

RAG 的核心不是向量数据库，而是“检索—增强—生成”这条数据流。建立索引时，程序先切分文档并生成 Embedding；回答问题时，再检索最相关的 Chunk，把内容和来源一起交给模型。

向量搜索适合语义匹配，关键词搜索适合精确词语，结构化搜索适合目录和文件组织清楚的数据。它们可以组合使用，不必互相替代。

RAG 也不会自动保证答案正确。系统需要分别评估检索和生成两层，并保留来源、分数和文档标识。把检索包装成 Agent 工具以后，还可以利用 Callback 完成结果压缩、权限控制和人工确认，让知识检索真正进入可追踪、可控制的执行流程。
