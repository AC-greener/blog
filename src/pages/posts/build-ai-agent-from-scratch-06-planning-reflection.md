> 上一篇解决了 Agent 如何保存执行历史、延续 Session，并控制不断增长的上下文。这一篇继续解决方向问题：当一个任务需要多步协作时，Agent 怎样知道自己要去哪里，又怎样发现自己已经走偏。

## 1. 能连续行动，不等于知道怎样完成任务

ReAct Agent 的基本循环是：观察当前上下文，选择一个行动，读取行动结果，然后决定下一步。

```text
观察 → 行动 → 获得结果 → 再观察
```

这套循环适合短任务。例如查询天气时，Agent 调用一次搜索工具，再整理结果，任务就结束了。

复杂任务不同。假设用户要求：

```text
查找一名运动员的马拉松纪录，再计算他用相同速度跑完地月距离需要多久，最后核对来源。
```

这个任务至少包含资料检索、数据核对、单位换算、计算和结果说明。Agent 如果只盯着眼前一步，容易出现以下问题：

- 查到一部分资料就过早回答。
- 忘记已经完成的搜索，反复调用同一个工具。
- 同时得到多个数字，却不知道它们怎样组合。
- 工具失败以后不断重试，没有寻找替代方案。
- 做了很多操作，却没有检查是否满足原始要求。

问题不在于 Agent 不会行动，而在于行动之间缺少一条可以检查的路线。

Planning（规划）负责写下这条路线，Reflection（反思）负责检查目前是否仍沿着路线前进。

## 2. Planning 和 Reflection 分别解决什么问题

这两个概念经常一起出现，但职责并不相同。

| 能力 | 回答的问题 | 典型输出 |
| --- | --- | --- |
| Planning | 接下来需要完成哪些阶段？ | 任务列表、顺序和完成状态 |
| Reflection | 当前进度和结果是否仍然有效？ | 继续、换方法或重新规划 |

Planning 发生在行动之前或计划失效之后。Reflection 发生在获得阶段性结果、遇到错误或准备结束的时候。

它们也不同于上一篇的上下文摘要：

```text
摘要：过去发生了什么？
规划：接下来应该做什么？
反思：现在的做法还对不对？
```

摘要的主要目标是减少上下文；规划和反思的目标是改变后续决策。

## 3. Planning：先把“大任务”拆成可以检查的阶段

对于前面的研究任务，一份最小计划可以是：

```text
1. 查找并核对运动员的马拉松纪录
2. 查找地月距离，并统一计量单位
3. 根据两个结果完成计算
4. 检查计算过程和资料来源
5. 生成最终回答
```

计划的价值不是提前猜中每一个操作，而是让 Agent 和程序都能看见：哪些工作已经完成，哪些仍然缺失。

### 3.1 用任务状态表示进度

一份简单计划至少需要任务描述和状态。下面是示意代码，仓库当前尚未实现对应模块：

```ts
type TaskStatus = "pending" | "in_progress" | "completed";

type Task = {
  id: number;
  description: string;
  status: TaskStatus;
};

function createTasks(tasks: Task[]): string {
  return tasks
    .map((task) => {
      const checked = task.status === "completed" ? "[x]" : "[ ]";
      return `${checked} ${task.id}. ${task.description}`;
    })
    .join("\n");
}
```

这个函数只负责把任务列表格式化为文本。真正的规划仍然由模型完成；程序则应该检查字段、保存计划，并把更新后的状态放回执行上下文。

只靠文本列表还不能保证计划一定可靠。程序至少要防止任务 ID 重复、状态值非法，以及计划不断变长却从不完成。

### 3.2 计划应该拆多细

任务太粗，Agent 看不出中间进度。例如“完成研究并给出答案”虽然正确，却几乎没有指导作用。

任务太细也不好：

```text
1. 打开搜索工具
2. 输入关键词
3. 读取第一条结果
4. 保存网页标题
```

这种计划把工具操作本身当成目标。Agent 每做一个小动作都要更新状态，会增加调用次数和上下文噪声。

更合适的粒度是一个有明确产出的阶段，例如“查找并核对马拉松纪录”。它可能需要多次搜索，但完成条件是得到经过核对的纪录，而不是打开过几个网页。

### 3.3 不是所有任务都需要计划

规划本身也有成本。模型需要生成、读取和更新计划，程序还要保存状态。

以下任务通常值得先规划：

- 需要多个工具协作。
- 包含几个前后依赖的阶段。
- 需要收集多份资料并交叉核对。
- 有明确且容易遗漏的完成条件。
- 失败后存在多种替代路线。

一次搜索、简单计算或直接问答，通常不需要额外计划。好的 Planning 工具描述既要说明什么时候使用，也要说明什么时候不要使用。

## 4. Reflection：不要等到最后才发现走错了

计划只能描述预期路线，执行过程中仍然会遇到错误、缺失资料和互相矛盾的结果。Reflection 让 Agent 在关键节点停下来检查：

- 当前阶段是否真的完成？
- 现有证据是否足以支持结论？
- 工具结果之间是否冲突？
- 失败来自工具，还是原计划本身？
- 应该继续、换一种方法，还是重新规划？

反思结果也可以通过一个工具写回上下文。下面同样是示意代码：

```ts
function reflect(
  analysis: string,
  needReplan = false,
): string {
  return needReplan
    ? `Reflection recorded (REPLAN NEEDED): ${analysis}`
    : `Reflection recorded: ${analysis}`;
}
```

`analysis` 记录当前判断，`needReplan` 则提供一个明确的协调信号。不过，这个布尔值只是模型给出的建议，程序仍然需要控制最大重规划次数和总执行步数。

### 4.1 在什么时候触发 Reflection

如果每次工具调用后都反思一次，Agent 会把大量时间花在检查自己，而不是完成任务。

更有价值的时机是：

- 完成一个计划阶段以后。
- 工具失败或连续返回空结果时。
- 两份资料互相矛盾时。
- 计划依赖的前提被否定时。
- 准备生成最终回答以前。

进展顺利时，Agent 可以继续执行。Reflection 主要用于容易走偏或需要验收的节点。

## 5. 方法失败，不一定需要重新规划

假设 Agent 原计划使用 Wikipedia 查找资料，但工具暂时不可用。

```text
调用 Wikipedia → 工具失败
        ↓
Reflection：目标仍然有效，改用 Web Search
        ↓
调用 Web Search → 继续原计划
```

这里失败的是方法，不是计划。研究目标和后续计算仍然成立，所以不需要把整份任务列表推倒重来。

另一种情况是，搜索结果证明用户给出的运动员根本没有公开马拉松纪录。此时后面的速度计算失去了输入，原计划已经无法完成。Reflection 应该指出前提不成立，并触发重新规划，例如改为说明资料不足，或者向用户确认是否使用另一组数据。

可以用一句话区分：

```text
换工具能继续完成原目标 → 调整方法
原目标或任务依赖已经失效 → 重新规划
```

Reflection 不是自动修复器。它只是把“发生了什么、建议怎样处理”写进上下文，下一轮仍然由模型选择行动，程序负责执行限制和权限控制。

## 6. 把计划、执行和反思放进同一个循环

在现有 Agent 架构中，Planning 和 Reflection 可以被设计成普通工具。模型调用它们后，工具结果进入 `ExecutionContext.events`，并影响下一轮模型请求。

下面的代码只展示控制流程，并不是仓库中可直接运行的实现：

```ts
async function runComplexTask(question: string) {
  const context = new ExecutionContext();

  while (!context.finalResult && context.currentStep < maxSteps) {
    const response = await agent.think(context);
    context.addEvent(response);

    if (hasToolCall(response, "create_tasks")) {
      await agent.executePlanningTool(context, response);
    } else if (hasToolCall(response, "reflection")) {
      await agent.executeReflectionTool(context, response);
    } else {
      await agent.executeOtherTools(context, response);
    }

    context.incrementStep();
  }

  return context.finalResult;
}
```

这段示意代码延续了前面的 ReAct Loop。变化只在于工具箱里多了两类工具：

- `create_tasks` 创建或更新计划。
- `reflection` 记录检查结果和是否需要重规划。

当 Reflection 建议继续时，Agent 执行下一个未完成任务；建议更换方法时，Agent 保留计划但选择其他工具；只有计划依赖失效时，才重新调用 `create_tasks`。

真实实现还需要决定计划存在哪里。一种自然的做法，是把当前任务列表放入 `ExecutionContext.state`，把每次计划更新和反思结果作为 Event 保存。这样，状态用于快速读取，事件用于解释计划为什么发生变化。

## 7. 规划和反思也需要程序边界

Planning 和 Reflection 都由模型生成，因此不能把它们当成绝对正确的控制器。程序仍然需要设置边界：

- 最大执行步数，防止 Agent 永远不结束。
- 最大重规划次数，防止反复推翻计划。
- 工具调用白名单和参数校验。
- 明确的完成条件，避免任务状态停在 `in_progress` 却直接回答。
- 错误分类，区分可重试错误、永久失败和权限拒绝。
- 日志或事件记录，解释每次计划变化的原因。

还要注意额外成本。Planning 会增加一次或多次模型决策，Reflection 也会增加上下文和调用。只有任务复杂度足以抵消这些开销时，它们才有价值。

计划也不是事实，反思更不是验证结果。涉及计算、外部资料和高风险操作时，仍然要依靠工具结果、来源、业务规则和人工确认。

## 8. 把整篇压缩成一张流程图

```text
收到复杂任务
     ↓
Planning：拆分阶段和完成条件
     ↓
执行当前阶段需要的工具
     ↓
Reflection：检查结果和进度
     ↓
 ┌────────────┬────────────┬────────────┐
 │ 继续原计划 │ 更换执行方法 │ 重新制定计划 │
 └────────────┴────────────┴────────────┘
     ↓
满足完成条件后生成最终回答
```

Planning 让 Agent 看见目的地和中间站，Reflection 则检查它现在位于哪里。两者都不替代执行工具，也不替代程序的安全边界。

## 总结

ReAct 让 Agent 根据当前观察选择下一步行动，但复杂任务还需要一条可以检查的执行路线。

Planning 把目标拆成有明确产出的阶段，并记录完成状态；Reflection 在阶段结束、错误发生或准备回答时检查结果，判断应该继续、更换方法还是重新规划。

二者结合以后，Agent 不再只是对最新工具结果作出反应，而是能够围绕整体目标持续执行。不过，规划和反思同样会出错，也会增加延迟和 token 成本。程序仍然必须限制步数、重规划次数和工具权限，并用真实结果验证模型给出的判断。

当前仓库尚未实现 `step7` 的 Planning 与 Reflection 模块，因此本文代码均为架构示意。真正落地时，可以复用前面已经构建的 `ExecutionContext`、Event、工具接口和 Agent Loop。
